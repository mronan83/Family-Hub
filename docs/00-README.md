# FamilyWise — Project Brief (v0.8)

A family "digital board" for a 32" 4K touch display (Raspberry Pi 5 kiosk) holding the whole family's chores and to-dos in one list: everyone sees who is doing what, a child's work earns points to spend in a rewards shop and progress toward goals, and parents manage everything, including their own tasks, from phone or laptop. The board is only the interactive front end. Apple Calendar remains the system of record for events. Hosted on Vercel + Supabase.

## Document map

Claude Code produces, maintains and manages the five build artifacts below, the user guide (`07`) for the family, and the test strategy (`08`). Every PR that changes behavior, schema, scope or sequence updates the affected artifact in the same PR, bumps its version line, and adds a row to `04` §I. ## Key decisions

| ID | Decision |
|---|---|
| D-01 | Board and admin are the system of record for chores, rewards, meals, school year. Apple Calendar owns events; sync is read-only. |
| D-02 | Next.js (App Router, TypeScript) on Vercel; Supabase for Postgres, Auth, Realtime, Vault, `pg_cron`. |
| D-03 | Completions are immutable events (truth). `chore_occurrence.status` is a persisted, rebuildable projection of them; progress and history tables are projections too. |
| D-04 | Occurrences are materialized one per chore per due date and shared by its assignees (D-30). A day-close job marks unfinished routines `missed` and finalizes the day, so good and bad streaks can be shown over time; tasks carry over instead (D-31). |
| D-05 | Day type (school day, break, weekend, summer, no school) is resolved from school-year config and drives chores and lunch. |
| D-06 | The board is a device principal (a Supabase Auth user with scoped `app_metadata`), revocable instantly via RLS. |
| D-07 | Offline-first board: PWA, IndexedDB snapshot, idempotent outbox. |
| D-08 | School menu import is an adapter with CSV/manual fallback; manual overrides are never overwritten. |
| D-09 | `household_id` on every table, RLS everywhere. |
| D-10 | Reward logic is a pure, isomorphic TypeScript package, property-tested. |
| D-11 | iCloud via published ICS first; CalDAV only with a secondary read-only Apple ID. |
| D-12 | Schedules via `pg_cron` + `pg_net` calling signed Vercel job endpoints. |
| D-13 | Points are an append-only ledger (earn, reversal, bonus, spend, refund, adjustment). Parents define a reward/activity catalog with point costs; the child requests, a parent approves. Goals can pay out points or a catalog item. |
| D-14 | The approval workflow is a household on/off switch with a per-chore override. Off: the child's check-off counts at once, a parent verifies in real life and can uncheck (reversing points). On: check-offs wait for approval. Insights show reversal and rejection rates to guide the setting. |
| D-15 | Admins choose which calendars each board shows (`device_calendar`). |
| D-16 | Reference panel is 3840×2160 at 32"; UI is laid out at 1920×1080 logical px with device scale factor 2 (since D-73 the board zooms itself to any screen, so the scale factor no longer matters). SPIKE-03 decides whether 4K animation is viable on the Pi 5 or the 1080p fallback applies. |
| D-17 | Everything derived from completion state is reversible: reversing a completion takes its points away (the balance can go negative) and un-achieves any goal it satisfied, reversing the payout. |
| D-18 | The product is named FamilyWise. Brand tokens and assets in `brand/` are the single source for color, type, and icons; the board never uses red for child-visible states and never relies on color alone (NFR-13). |
| D-19 | **Single launch.** Nothing goes live until every phase (P0–P3) is built and the launch acceptance checklist (`04` §E) passes. Phases are build milestones, not release gates. Scope is fixed; no feature is cut. |
| D-20 | **Event time decides.** An occurrence's status folds its events in `occurred_at` order (latest wins), online or offline; ties break on `recorded_at`, then `id`. The database clamps `occurred_at` to no later than the time it was received. |
| D-21 | **Today on the board.** The board shows today's items and any open overdue tasks (D-31). Late credit for a past day's routine is parent-only (`admin_complete`). A board event on a routine whose `occurred_at` falls outside its due date (household-local) is stored as `flagged` and waits for a parent. |
| D-22 | Switching approval on or off re-resolves `scheduled` occurrences only. Check-offs already waiting for approval stay in the queue; completed ones are unchanged. |
| D-23 | Day-close finalizes both `scheduled` and `rejected` occurrences as `missed`. |
| D-24 | A school closure added for today leaves today's occurrences untouched; only later dates are regenerated. |
| D-25 | Admin sign-in: email magic link and email + password are required (ACC-02). Sign in with Apple and passkeys follow once the production domain is fixed (ACC-06). |
| D-26 | **Delivery without Docker or staging.** CI tests the database on a native Postgres with a Supabase compatibility bootstrap and pgTAP. Each PR gets a Vercel preview that runs as the demo family on the test database (D-85). Merging to `main` applies migrations, then deploys the app, to the production project, which stays dark until launch (`01` §9). |
| D-27 | Three reward models stay as scoped: goals (with their own achieve → redeem lifecycle), shop redemptions, and wishlist pins. |
| D-28 | The points ledger is written only by `SECURITY DEFINER` database functions: earn and reversal by trigger; spend, refund, adjustment and bonus by named functions the API calls. |
| D-29 | **Free plans only.** Supabase Free (two projects: production, and the test database previews and e2e use, D-85), Vercel Hobby, GitHub Free. A keepalive prevents inactivity pausing, backups are our own nightly encrypted dumps, and CI reaches the database through the session pooler (`01` §9.10). |
| D-30 | **One family list.** Chores and tasks for every member, adults included, live in one model. Owners are family members (assignees), never tags. Each item has one occurrence per due date shared by all its assignees: whoever does it is recorded (`done_by`) and it is done for everyone; for an assignee who did not do it, it counts as `covered` (neutral). |
| D-31 | **Routines and to-dos.** A chore is a routine: if it is not done on its day, day-close marks it `missed`. A task is a to-do, one-off or repeating: it stays open and shows as overdue until it is done or cancelled, and is never `missed`. An optional due time orders and groups the day and marks lateness; it never changes scoring. |
| D-32 | **Rewards follow the person.** Each member has an earns-rewards switch, on for children and off for adults by default. Points, the approval workflow, goals and reward streaks apply only to credited members with it on. |
| D-33 | **Tags are a household list.** Tags (name, color, icon) are defined by admins and referenced by id. Goals, filters and insights measure by tag, so renaming or archiving a tag never breaks a goal. |
| D-34 | **Family-visible unless private.** Every item shows on the board and to both parents unless it is set private; a private item is visible only to the admin who created it and to assignees who sign in, enforced by RLS. Anyone at the board can check off any family-visible item; the event records who did it and that it came from the board. |
| D-35 | **Reminders are web push, and switchable.** Parents' reminders are web push notifications to the admin app (added to the iPhone Home Screen, or a desktop browser). They are off until a person turns them on, and switchable per person, per device and per item. Each item reminds each person at most once and never after it is done; quiet hours hold them; private items hide their title on the lock screen. No email or SMS: Supabase's built-in email is limited and SMS costs money (D-29). |
| D-36 | **Gates enforced at deploy.** The repository stays private, and GitHub Free does not enforce branch protection, environment secrets or required reviewers on a private repository. The deploy workflow enforces the pull request gates instead: it ships only the head of `main`, and only if it came from a merged pull request, passed every CI check, and its pull request passed e2e on its preview. Production secrets are repository secrets. Merges are squash only. Rejected: a public repository (protection is free there, but the family's design and its full history become public for good) and GitHub Pro (against D-29). |
| D-37 | **One database, and you approve what ships.** The loop: you give requirements; Claude Code develops, tests and opens the pull request; you preview; you approve; Claude Code merges and deploys. Previews use the production Supabase project and run as the **demo family**, a separate household with made-up members that RLS keeps apart from yours, as it would any two families. Previews hold only the browser-safe key, so nothing in a preview can bypass RLS; the secret key and jobs exist only in production. A pull request's new database changes are applied when its preview is tested, unless one removes or renames something; those wait for your approval and ship with the deploy. Nothing in the pipeline ever wipes the database. The second free Supabase project stays unused. Rejected: a separate preview project (uses the second free slot) and a throwaway Supabase in CI (needs Docker). Previews and e2e moved to the second project in D-85. |
| D-38 | **Jobs answer at once, and nobody handles the job secret.** SPIKE-05 measured job calls on Vercel Hobby (`01` §5.6). pg_net holds every queued call until its slowest call finishes, and calls that start together each pay a cold start, the costliest thing on Hobby's Active CPU allowance. So each job endpoint answers at once and does its work after the response, every schedule has its own minute, and a job's health comes from its own `job_run` record, not from the scheduler. The job secret is generated by a workflow straight into Supabase Vault and Vercel production, and rotating it is the same workflow. Jobs stay under 10 % of each Hobby allowance. Rejected: Vercel Cron (Hobby runs it at most once a day, give or take an hour) and moving the database-only jobs into Postgres (not needed at this budget, and it would split the rules between TypeScript and SQL). |
| D-39 | **Private by invitation; nobody types a demo password.** FamilyWise has no public sign-up. A new household starts from a one-time setup code that a workflow issues (24 hours, shown only on the run's page). Every other admin joins through an invite link the inviter copies or shares: it works once, for 7 days, and only for the email it names. The server creates each new account already confirmed, so nobody depends on Supabase's built-in mailer, which reaches only the Supabase team: the second admin signs in with a password, and magic links reach everyone once custom email exists (Y-8). Tokens and codes are stored only as hashes, and an invite token rides after `#` in the link, so no server log holds it. Previews sign in with one tap as made-up demo parents. Their passwords are derived from the preview-protection secret that Vercel and e2e already hold, so previews still carry no key that bypasses RLS. Every change to a household's tables is audited by a database trigger, so no later screen can forget to. Rejected: public sign-up with email confirmation (the mailer cannot reach the second admin), Supabase's invite email (same limit), and a `withAudit` wrapper in the API layer (a route that forgets it goes unaudited). |
| D-40 | **A board pairs in the database, and heals itself.** A board is a Supabase sign-in of its own, created by a database function when the board enters an 8-digit code an admin got in Boards (one use, 10 minutes). Because the database creates it, previews pair exactly as production does, with no secret key, so e2e tests the real path on every pull request. The board keeps its credential in a cookie the page cannot read and signs itself in again if its session ever lapses, so nobody has to re-pair a kiosk after a wifi hiccup. Disconnecting is final: the board reads nothing from that moment and its sign-in is banned. Wrong codes are counted across everyone; after 20 in 10 minutes pairing pauses, so guessing a code is hopeless. Rejected: Supabase's admin API (needs the secret key, so previews could not pair and the real path would go untested), anonymous sign-ins (a dashboard switch, and turned off with sign-up before launch), and 6-character codes (easier to guess, and the board has no keyboard: digits fit an on-screen keypad). |
| D-41 | **The board keeps its own snapshot live.** The server draws a board's first snapshot. From then on, when Realtime says something changed, the board reads `board_snapshot` again itself, straight from the database with its own session and under RLS. A burst of changes costs at most two reads, and the board reads again whenever it reconnects or the network returns, so nothing is missed. This keeps admin changes inside the 3-second budget (DEV-05), which e2e measures on every pull request. It also spends nothing of Vercel's Hobby allowance however often a family edits, and it gives the board the state that check-off (WP-11) and the offline cache (WP-13) build on. An admin can hold a board on Day or Evening instead of the clock (Boards). Rejected: re-running the server page on every change (the WP-05 stopgap: a Vercel invocation per change per board, slower, and nothing in the browser to cache) and drawing from Realtime's row payloads (partial rows, and derived data such as points cannot be patched safely, `01` §7). |
| D-42 | **System Health shows each household its own, and the deployment's costs.** A server error is kept with the household it happened for: a job's household, or that of whoever made the request (a board, or a signed-in admin). Each admin sees only their own household's jobs and errors. Errors on signed-out pages stay in the database for the operator and appear on no household's page. Every read goes through a database function that checks the caller is an admin, so previews, which never hold the secret key (D-37), show the same page. Usage is the deployment's, so any admin sees it. A daily workflow reads the Vercel account's usage with the deploy token, and the database's size is read live. Vercel's Hobby limits cover every project on the account, so the page shows the account's total and FamilyWise's share. Rejected: reading errors with the secret key on the server (previews could not show or test the page), showing every error to every admin (households would see each other's), and giving the app a Vercel token (another secret in production, for numbers that change once a day). |
| D-43 | **Only an item's creator decides who sees it; the day has four parts.** The admin who created an item is the one who makes it private or family-visible again, so the other parent can neither hide a family item from the board nor reveal someone's private one. If the creator's sign-in is deleted, the item stays, and the admin who next changes its visibility becomes its creator. An item, its assignees and its tags are saved together, in one transaction. Due times group the day: Morning (before noon), After school (noon to 5 pm), Evening (from 5 pm) and Anytime (no due time). Tags use the six categorical colors and always show their name. |
| D-44 | **Each member follows a school year, with the default as the fallback.** A member follows the school year they are assigned to on that date (a child at another school, say), and otherwise the household's default school year for that date. Several years can be defaults as long as their dates don't overlap, so next year's calendar can be added in the summer and simply starts on its first day; nobody switches anything. A member follows one school year on any date. Terms and days off sit inside their year; a year is archived, never deleted. Day types are always worked out by the database (`resolve_day_type`), never stored per day. |
| D-45 | **Occurrences are planned in the database two weeks ahead, and history never moves.** Each item has one occurrence per due date for today and the next 14 days, made by the database: an hourly job (`occurrence_gen`) fills tomorrow to 14 days ahead, and saving an item, its assignees, a member, a school year, a closure or who follows which year re-plans at once. Only an occurrence nothing has happened to ever changes, and never a past one. An item's own edit, or a member archived or restored, reaches today's occurrence in place: it keeps its id, so a check-off from the board, even one queued offline, still lands; an item archived in the morning leaves today, so it is never marked missed; someone added at 7 am has it today. A school-year change starts tomorrow, so today stays as planned (D-24). A monthly day past the end of a shorter month falls on its last day (the 31st is April 30). A one-off task entered after its date is made on that date and shows as overdue. Occurrences are derived: nobody writes them directly, and they are not audited (the edits that cause them are). |
| D-46 | **The database records who did what, and a board only checks off and undoes.** Every check-off, undo, approval, rejection, skip and correction is an append-only event. Who recorded it comes from the session (the board, an admin of that household, or the database itself), never from the request. A board can only check off and undo, and undo only a check-off made within the household's undo window by event time (2 minutes by default); everything else is a parent's. Events on one occurrence are recorded one at a time, so each status is folded from every earlier event. A batch answers each event on its own (recorded, duplicate, gone, refused or invalid), so one refusal never loses the rest. Events are their own audit trail and are not copied to the audit log. A nightly check re-folds the past 14 days and the planned 14 ahead and fails on any difference; correcting one is a parent's explicit action. |
| D-47 | **With several people, an item is either everyone's own or anyone's.** "Everyone does their own" (each) gives every assignee their own occurrence per due date, for things like making their own bed: each person's check-off, points and miss are their own, and each person's own day type decides whether it is due for them. "Any one of them" (shared) is D-30: one occurrence per due date, done by whoever gets to it and covered for the rest. A new chore starts as each and a new task as shared; the question is asked only once an item has two or more people, and either can be changed later. Items saved before this stay shared until someone changes them. Changing it follows D-45: today changes in place unless someone already acted on today's, so a day is never counted twice, and the past never changes. |
| D-48 | **The repository is public.** The owner made it public on Oct 9, when the private Actions allowance ran out: GitHub Actions is free for a public repository. Secrets stay in GitHub, Vercel and Supabase settings, never in the repository, and its full history was scanned and holds none. Run pages and artifacts are public too, so: e2e keeps no Playwright report (its traces record the deployment-protection bypass); the setup-code workflow issues no code while the repository is public; nightly backups (WP-24) are not kept as workflow artifacts. Previews of pull requests from forks need the owner's authorization in Vercel (fork protection), and e2e runs with the database credential only on commits already on one of this repository's branches. Supersedes D-36's choice of a private repository; its deploy gate stays, and the branch protection GitHub now offers can be added. |
| D-49 | **Points follow the status, and a balance is a sum.** The points ledger is append-only: nothing in it is edited or deleted, and a mistake is put right with a new entry. An occurrence owes its points to each member it rewarded while it is done (completed or approved), and nothing otherwise. Every status change posts the difference between what it owes and what the ledger already holds, so whatever changed the status (a check-off, an undo, an approval, day close, a parent's rebuild) the ledger agrees, and posting again posts nothing. Check-offs recorded before the ledger existed earned their points when it arrived, dated when they were done. A parent adds or takes away 1 to 10,000 points with a reason, as themselves, only for a member who earns rewards and is not archived; the form's request id makes a double tap post once. A balance may go below zero and shows as points to earn back. Only database functions write the ledger: not the app, not the service role. The board's snapshot carries each rewarded member's balance and five latest entries; a private item's points count there without its title. The nightly status check also fails when a member's points for an occurrence differ from what it owes them. Refines D-28. |
| D-50 | **The board's Today answers a tap at once, and never tells anyone off.** The board opens on everyone's day, a column per person; tapping a person shows their own day with their points, and it goes back to everyone after 90 seconds untouched. It shows today's items and open overdue tasks (D-21), Overdue first, then Morning (before noon), After school (from noon), Evening (from 5 pm) and Anytime; private items and archived items never reach it. A tap shows the check-off at once and sends it to `POST /api/completions` with an id the board makes, so a double tap or a resend counts once, and a second tap on the same tile within half a second is ignored. The board shows its own check-offs on top of the snapshot until a snapshot read after the database answered shows them. On a person's own screen a tap credits that person. In everyone's view it credits the column's person for their own item or an item with one person, and asks who did a shared item with several (its people first, then anyone, several allowed). Undo is its own button under a done tile for the household's undo window, counted from the check-off, and needs a second tap within 4 seconds; after the window, a parent changes it. A child's check-off that earns points celebrates: the check pops and the balance counts up over about 600 ms. With reduced motion the balance changes at once and nothing moves. An adult's check-off does not celebrate. A person's own screen lists their five latest points entries by what each was for. Points a parent took away read only "A parent changed your points": the reason stays in the admin app, so the family screen never shows why a child lost points (`06` §2). Until WP-13, a board keeps unanswered check-offs in memory and retries them with backoff. The board reads its snapshot again at the household's midnight. The owner confirmed on Oct 9 that the reason for points taken away stays off the board. |
| D-51 | **How the rules engine reads a day and a goal.** The engine (`packages/rules-engine`) is pure: the same facts give the same result in any order and any time zone. A day is judged on a member's routines only; tasks never make a day good or bad (D-31). A day is: neutral when nothing counts (none, or all skipped or covered); good once enough is done, **today included the moment it qualifies**, so a child sees the streak grow when they finish rather than after midnight; open while anything is still to do or waiting for a parent, and always today, so it is never bad; bad only for a past, settled day without enough done. Runs pass over neutral and open days. A streak goal's target, once reached, stays met while the days that reached it stay done, so a later bad day does not take the goal back; until then its progress is the run going now. A scope of items and tags counts an item that matches either. A parent's late credit can still achieve a goal after its end date, counting only days inside its window. Refines `02` §5. |
| D-52 | **A parent's day.** The admin app's Today page shows check-offs waiting for a parent first (from any day), then a day's items by part of day, with today's overdue tasks. A parent can go back to any past day for late credit, and ahead to skip. A routine can't be marked done before its day; a task can be done any time. "Mark done" credits the item's own person or its one assignee; a shared item with several asks who did it (its people first, anyone allowed). "Not actually done" unchecks the ticked done items together as one batch: the form's request id is the batch id, so a form sent twice is one batch, and each item's points are reversed once. Undo puts back what is unchanged since, as a parent's completion (approved) by whoever had done it, and earns its points again; anything changed since stays as it is. The approval switch is on Home (each item can still always or never need a parent); switching changes only what is still to do (D-22). My tasks is for the member linked to the parent's sign-in: their overdue tasks, today's items and the next seven days, shared ones included. Marking one done credits only them. Quick add makes a family-visible task for them today, with no points. Every action is a completion event recorded as the parent (D-46). |
| D-53 | **The rewards shop.** A parent keeps the shop: rewards and activities, each with a cost, an optional description, an icon or photo, an optional stock and a weekly limit per child; archived rather than deleted. A child asks for one on the board. The request is accepted only while their balance less what they have already asked for covers the cost, the reward is in the shop, there are any left (counting requests waiting, approved and given), and they are under its weekly limit for the household's week. These checks run under a lock on the child and on the reward, so two requests at once cannot overspend or take the last one twice. The board's request id makes asking twice one request. A child can cancel on the board while it is waiting. A parent approves it (the points are spent: one `spend`, named for the reward, so the board's points list says what they went on), says "Not this time" (nothing spent), marks it given, or cancels it. A cancel refunds an approved reward; one already given is not cancelled. Photos are JPEG, PNG or WebP up to 2 MB, in a private bucket with a folder per household. Its parents add and remove them, and its boards and parents read them through links that last an hour. The board's shop screen and its slice of the snapshot come with WP-20. |
| D-54 | **The board works through an outage.** A board keeps its outbox, its last snapshot and the check-offs it is showing ahead of the snapshot in IndexedDB (Dexie), for the paired board only: paired again as another device, it starts empty. What it had not sent goes first, oldest first, with the ids it was made with, so a reload or a retry records nothing twice; it sends at once when the network returns. The service worker stays the project's own small script, not Serwist: it precaches the fonts, keeps the build's content-hashed files as the board loads them, and keeps the board's page, used only when there is no network (a slow or redirecting server is always followed). Serwist's Turbopack build needs a route handler and native build tools, and would precache every page's files on every admin phone; the board needs only its own. The board says "Offline: your check-offs are saved" while it has no network or cannot send, and "Updated 12 minutes ago" once its snapshot is over five minutes old (it reads again every four minutes, so a quiet household is never stale), or "Today's list may be out of date" when planning or day closing is late or erroring (`job_health()`, through job_run's RLS). ## Build order

1. **Spikes** where they gate work (see `05` §4): SPIKE-01 device sessions + Realtime under RLS and SPIKE-05 job limits before P0 device and job work; SPIKE-02 before calendar sync; SPIKE-04 before menu adapters; SPIKE-03 when the Pi and panel arrive.
2. **P0** foundation, **P1a** kid loop (incl. school year and points ledger), **P1b** rules engine + shop + streak history, **P1c** goals, **P1d** calendar + hardening, **P2** meals + menu + extras, **P3** polish. Milestone exit criteria are in `04` §E; work package order and dependencies are in `05`.
3. Work proceeds in dependency order. A milestone is done when its exit criteria pass in CI and on a preview; independent work packages may run in parallel. Sequence is chosen so no completed work package needs rework.
4. **Launch** once all milestones are done and the launch acceptance checklist (`04` §E) passes on the real Pi and panel.

## Conventions for Claude Code

- One branch and one PR per work package; prefix commits and test names with requirement IDs: `[CHR-04] ...`.
- End every commit message, the squash merge's included, with `Co-Authored-By: Claude <noreply@anthropic.com>` and `Claude-Session: <session URL>`; no model name or ID in a commit, PR, comment or doc (D-125).
- Writes go through API routes or server actions; the board never writes to tables directly.
- Never take `household_id` from client input; derive it from the verified session.
- All schema changes via Supabase CLI migrations; every new table ships with RLS and pgTAP coverage.
- No Docker anywhere in the workflow. Database tests run on native Postgres (`scripts/db-test.sh`).
- Keep the rules engine free of I/O and clocks (inputs only).
- Keep `04` Stories, Work packages, Tests, coverage and component sections, and `08`'s Test catalogue, generated (`--fix`), not hand-edited.
- Write an item's test cases (`MEAL-11-a`) in its `05` §5 section before building it, give each a test that names it, and test each change by its class (`08`; D-106, D-107).
- `chore_occurrence.status` and the points ledger are written only by the database functions in `02` §4.2 and §4.2b; never update them from application code.
- Work runs as a planner session and one worker session per item; `CLAUDE.md` and `.claude/skills/` hold the rules and the definition of done (D-90).
- Tests follow the test standard (D-110, `CLAUDE.md` "Tests"): no fixed waits, no real clock, each test's own data and no order, limits from measured runs with 3× headroom, Vitest and the UI suite before e2e. e2e runs nightly only (D-108); a failure re-runs once only on evidence the infrastructure caused it.
- Update the affected artifact (`01`–`05`) in the same PR as the change, and log it in `04` §I. Update the user guide (`07`) in the same PR as any user-facing change, tag each section with the stories it covers (`<!-- covers: US-nnn -->`), and retake its screenshots with `pnpm guide:shots` when a screen changes (D-68).
